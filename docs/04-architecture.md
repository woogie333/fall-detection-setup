# RDK X3 다중센서 낙상 감지 시스템 — 설계 문서

작성일: 2026-08-13

---

## 0. 확정된 하드웨어

| 역할 | 부품 | 인터페이스 | 비고 |
|---|---|---|---|
| 열화상 | FLIR Lepton 3.0 + PureThermal | USB (UVC) | 160×120, non-radiometric |
| mmWave | HLK-LD2450 | UART 256000 8N1 | 최대 3인 x/y/속도 추적, 10Hz |
| 충격 | ADXL345 (SW-420 대체 권장) | I2C (0x53) | 3축 ±16g, 내장 인터럽트 |
| 연산 | RDK X3 | — | Ubuntu, arm64 |
| 출력 | SmartThings 허브 | LAN/HTTP | Edge Driver |

### SW-420 → ADXL345 교체에 대해

비용은 3천~5천 원 수준으로 부담이 없고, 얻는 것이 큽니다. SW-420은 "임계값 넘음/안 넘음"만 알려주지만
ADXL345는 충격의 **크기·지속시간·방향**을 실수로 제공합니다. 이 차이가 "사람이 넘어짐"과
"의자를 끌었음"을 가르는 정보입니다. 배선도 I2C 4선(VCC/GND/SDA/SCL)이라 오히려 간단합니다.

MPU6050도 가능하지만 ADXL345를 권합니다. 자이로가 불필요하고, 내장 Activity/Freefall 인터럽트를
쓰면 CPU를 거의 안 먹으면서 충격 순간만 깨울 수 있기 때문입니다.

## 1. 각 센서가 실제로 할 수 있는 일

설계에서 가장 중요한 부분입니다. 각 센서의 **한계**를 정확히 알아야 융합 로직이 성립합니다.

### LD2450 — 위치는 알지만 높이는 모른다

LD2450은 **수평 평면상의 2D 좌표**만 출력합니다. x는 좌우, y는 센서로부터의 거리이고,
**z(높이)는 측정하지 않습니다.** 따라서 "사람이 아래로 떨어졌다"를 직접 볼 수 없습니다.

LD2450이 실제로 기여하는 것:

- 사람이 있는지, 몇 명인지 (최대 3명)
- 바닥 평면상 어디에 있는지 (mm 단위)
- 이동 속도 (cm/s, 부호 있음)
- 낙상 직후의 **정지 상태 지속** — 이게 핵심 기여입니다

낙상 시나리오에서 LD2450의 전형적 패턴은 "속도 급증 → 위치가 한 점에 고정 → 장시간 미세 움직임만".
넘어진 뒤 스스로 못 일어나는 상황이 정확히 이 패턴입니다.

### Lepton 3.0 — 자세를 본다

높이 정보를 담당하는 센서입니다. 벽면 1.5~2m 높이에 수평으로 설치하면
사람의 열 실루엣이 화면에서 차지하는 **세로/가로 비율과 무게중심 높이**를 볼 수 있습니다.

- 서 있음: 세로로 긴 blob, 무게중심이 화면 중상단
- 앉음: 중간 비율, 무게중심 중단
- 누움/쓰러짐: 가로로 긴 blob, 무게중심이 화면 하단

non-radiometric이라 절대온도는 없지만, 사람은 배경보다 확실히 밝게 나오므로
**적응형 임계값 + 연결요소 검출**로 충분히 분리됩니다.

### ADXL345 — 충격의 크기를 본다

바닥 구조에 물리적으로 결합되어야 의미가 있습니다. 벽에 붙이면 진동이 감쇠되어 못 잡습니다.
바닥재 위 또는 바닥과 맞닿은 가구 하단에 단단히 고정하세요.

기여: 낙상은 "짧고 큰 충격 1회"입니다. 발소리는 작고 반복적, 물건 떨어짐은 크지만
그 후 사람의 위치·자세 변화가 없습니다. 즉 ADXL345 단독으로는 판정 불가이고,
**다른 센서의 후보를 확증하거나 기각하는 용도**입니다.

## 2. 센서 배치

```
        [벽면 1.8m]
   ┌──────────────────┐
   │  Lepton (수평)    │  ← 감시 구역을 정면으로
   │  LD2450 (수평)    │  ← Lepton과 같은 방향, 나란히
   └──────────────────┘
            │
            │  감시 구역 (반경 약 4~6m)
            ▼
   ═══════════════════════  바닥
        ▲
     ADXL345 (바닥 결합)
```

**주의사항**

- Lepton과 LD2450은 **같은 방향을 보게** 나란히 두세요. 좌표 정합이 쉬워집니다.
- LD2450은 금속판이나 전자레인지 근처를 피하세요. 24GHz 반사/간섭이 생깁니다.
- Lepton은 직사광선, 라디에이터, 창문을 화각에서 제외하세요. 큰 열원은 오검출의 주범입니다.
- 두 센서의 화각이 다릅니다. LD2450은 ±60° 정도로 넓고 Lepton 3.0은 약 57° HFOV입니다.
  겹치는 영역만 "고신뢰 구역"으로 다루는 편이 안전합니다.

## 3. 소프트웨어 구조

단일 프로세스에 스레드 3개 + 융합 루프를 두는 구조를 권합니다.
프로세스를 나누면 IPC 때문에 시간 동기가 어려워집니다.

```
fall_detect/
├── sensors/
│   ├── thermal.py      # UVC 캡처 → 자세 특징 추출
│   ├── radar.py        # LD2450 UART 파싱 → 트랙 리스트
│   └── impact.py       # ADXL345 I2C → 충격 이벤트
├── fusion/
│   ├── buffer.py       # 시간 정렬 링버퍼 (공통 타임스탬프)
│   └── decider.py      # 상태머신 + 스코어링
├── output/
│   └── smartthings.py  # HTTP POST → edgebridge
├── config.yaml
└── main.py
```

각 센서 스레드는 자신의 샘플에 `time.monotonic()` 타임스탬프를 찍어 공유 링버퍼에 넣고,
융합 루프는 10Hz로 돌며 최근 N초 윈도우를 조회합니다.
**센서마다 주기가 다르므로(레이더 10Hz, 열화상 9Hz, 가속도 이벤트성) 공통 시계가 필수입니다.**

## 4. 센서별 구현 핵심

### 4.1 LD2450 파싱

프레임: 헤더 `AA FF 03 00` + 타깃3개×8바이트 + 테일 `55 CC` = 30바이트, 10Hz.

타깃 8바이트 = x(int16, mm), y(int16, mm), speed(int16, cm/s), resolution(uint16, mm)

**부호 인코딩에 함정이 있습니다.** 일반적인 2의 보수가 아닙니다.
최상위 비트가 **1이면 양수, 0이면 음수**입니다.

```python
def decode_signed(raw: int) -> int:
    # raw: 리틀엔디안으로 읽은 uint16
    if raw & 0x8000:
        return raw - 0x8000      # MSB=1 → 양수
    else:
        return -(raw)            # MSB=0 → 음수
```

이걸 2의 보수로 잘못 처리하면 좌표가 통째로 뒤집혀서 며칠을 날립니다.

사용하지 않는 타깃 슬롯은 8바이트 전부 `0x00`입니다. 이걸 "원점에 사람 있음"으로
오인하지 않도록 반드시 걸러내세요.

RDK X3에서 256000 baud는 비표준 속도라 드라이버가 거부할 수 있습니다.
`pyserial`로 안 되면 `termios2` / `BOTHER` 방식의 커스텀 baud 설정이 필요합니다.

### 4.2 Lepton 특징 추출

PureThermal은 UVC이므로 `/dev/videoN`으로 잡힙니다. 두 가지 포맷이 나옵니다.

- **YUV/RGB**: 보드가 AGC를 적용한 보기 좋은 영상. OpenCV로 바로 읽힘. 처리는 쉽지만
  자동 스케일링 때문에 프레임 간 밝기 기준이 흔들립니다.
- **Y16**: 14비트 raw. 프레임 간 일관성이 있어 **이쪽을 권장**합니다.
  OpenCV `VideoCapture`에 `CAP_PROP_CONVERT_RGB = 0` 설정이 필요합니다.

추출할 특징:

| 특징 | 의미 |
|---|---|
| `blob_area` | 사람 크기 (거리 보정 필요) |
| `aspect_ratio` = h/w | 서 있음(>1.5) vs 누움(<0.7) |
| `centroid_y_norm` | 무게중심의 화면 내 상대 높이 (0=위, 1=아래) |
| `d(centroid_y)/dt` | 하강 속도 — 낙상의 직접 증거 |

Lepton은 주기적으로 **FFC(셔터 보정)**를 수행하며 이때 약 0.5초간 화면이 얼어붙습니다.
이 구간을 낙상으로 오인하지 않도록, 프레임 차분이 비정상적으로 0에 가까우면 해당 구간을
스킵하는 가드를 넣으세요.

### 4.3 ADXL345

I2C 주소 0x53(SDO=GND) 또는 0x1D. 측정 범위는 ±16g, 출력 데이터율 100Hz면 충분합니다.

```
magnitude = sqrt(ax² + ay² + az²)
impact = magnitude 가 임계값(예: 2.0g)을 초과한 순간
```

폴링보다 **INT1 핀을 GPIO 인터럽트로 받는 방식**을 권합니다. ADXL345 내장 Activity 인터럽트를
설정해두면 평상시 CPU를 쓰지 않습니다.

## 5. 융합 판정 로직

단순 AND/OR는 실패합니다. **상태머신 + 시간창 스코어링**을 씁니다.

### 상태 전이

```
IDLE ──(트리거 발생)──> SUSPECT ──(확증 점수 충족)──> CONFIRMING
                           │                              │
                    (5초 내 미충족)                  (정지 30초 지속)
                           │                              │
                           ▼                              ▼
                         IDLE                           ALARM
                                                          │
                                              (움직임 재개 / 사용자 취소)
                                                          ▼
                                                        IDLE
```

### 트리거 (SUSPECT 진입) — 아래 중 하나

- ADXL345 충격 > 2.0g
- Lepton 무게중심 하강 속도가 임계 초과
- LD2450 속도 절대값 급증 후 급감

### 확증 점수 (5초 창에서 합산)

| 조건 | 점수 |
|---|---|
| Lepton `aspect_ratio` < 0.7 (누운 자세) | +3 |
| Lepton 무게중심이 화면 하단 1/3에 위치 | +2 |
| ADXL345 충격 > 2.0g | +2 |
| LD2450 트랙 존재 & 속도 ≈ 0 | +2 |
| LD2450 트랙 소실 (레이더 사각 = 바닥에 누움 가능성) | +1 |

**임계: 6점 이상 → CONFIRMING**

### CONFIRMING → ALARM

여기가 오검출을 막는 마지막 관문이자, 이 시스템의 가장 중요한 설계 판단입니다.

낙상 자체보다 **"넘어진 뒤 일어나지 못하는 상태"**가 실제 위험입니다.
스스로 일어나면 응급상황이 아니고, 알림을 보낼 필요도 없습니다.

따라서 CONFIRMING 진입 후 **30초간** LD2450 위치 변화와 Lepton 자세를 계속 봅니다.
이 사이에 일어서면 IDLE로 복귀, 계속 누워 있으면 ALARM.

30초 지연이 길게 느껴질 수 있지만, 오경보 한 번이 시스템 신뢰를 통째로 무너뜨립니다.
급하다면 15초로 줄이되 그 이하는 권하지 않습니다.

### 오검출 제외 규칙 (하드 필터)

- 침대/소파 영역의 좌표 사각형을 config에 등록하고, 그 안에서는 판정 비활성화.
  **이 규칙 하나가 오경보의 절반 이상을 없앱니다.**
- LD2450 트랙이 0개면 (사람 없음) 모든 판정 무시 — 반려동물, 로봇청소기 대응
- 최근 알람 후 3분간 재알람 억제

## 6. SmartThings 연동 (1단계: edgebridge)

낙상 로직 개발 중에는 Lua를 쓰지 않고 HTTP 한 줄로 끝냅니다.

1. SmartThings 앱에서 **edgebridge** 드라이버 설치 후 가상 센서 생성
2. PC 또는 보드에서 edgebridge 서버 실행
3. 보드는 알람 시 HTTP GET 하나만 전송

```python
import requests

def notify_fall():
    requests.get(
        "http://<edgebridge_ip>:8088/trigger/falldetect",
        timeout=3
    )
```

앱에서 알림이 뜨고 이력이 남습니다. 여기에 SmartThings 루틴을 걸면
조명 켜기, 문자 발송 등으로 확장됩니다.

### 2단계: 전용 Edge Driver

감지 로직이 안정된 후 진행합니다. 커스텀 Capability를 정의하면
`fallDetected`, `personCount`, `confidence`, `lastFallTime` 같은 값을 앱 UI에 직접 노출할 수 있습니다.
1단계 파이썬 코드는 그대로 두고 출력부만 교체하면 되므로 버려지는 작업이 없습니다.

## 7. 권장 개발 순서

각 단계마다 **동작을 눈으로 확인하고 넘어가세요.** 세 센서를 한꺼번에 붙이면
문제가 생겼을 때 어느 센서 탓인지 알 수 없습니다.

1. **LD2450 단독** — UART 파싱, 좌표를 터미널에 출력. 방을 걸어다니며 좌표가 맞는지 확인
2. **Lepton 단독** — UVC 캡처, blob 검출, aspect_ratio 출력. 서고 눕고 하며 값 변화 확인
3. **ADXL345 단독** — 충격 크기 출력. 발 구르기 / 물건 떨어뜨리기 값 비교
4. **edgebridge 연동** — 키보드 입력으로 가짜 알람 발생시켜 폰 알림 확인
5. **융합 로직** — 위 4개를 결합. 이 시점에는 각 부품이 검증되어 있으므로 로직에만 집중 가능
6. **임계값 튜닝** — 실제 환경에서 로그 수집 후 조정

**6번이 전체 작업의 절반입니다.** 문서의 점수와 임계값은 출발점일 뿐,
실제 방 구조와 설치 높이에 맞춰 반드시 조정해야 합니다.
그러려면 모든 센서 원시값을 CSV로 남기는 로깅을 1번 단계부터 넣어두세요.

## 8. 안전에 관한 고지

이 시스템은 **보조 수단**입니다. 어떤 센서 조합도 낙상을 100% 감지하지 못하며,
특히 감시 구역 밖, 가구에 가려진 위치, 화장실 같은 곳은 사각지대입니다.

실제로 고령자 보호에 사용하실 계획이라면 이 시스템만 믿지 마시고
응급 호출 버튼 같은 수동 수단을 반드시 병행하세요.
